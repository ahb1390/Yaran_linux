# معماری ساخت Yaran Linux

این سند توضیح می‌دهد که اجزای این مخزن چگونه کنار هم قرار می‌گیرند: `build.py` چه می‌کند، مانیفست‌های JSON چه چیزی را توصیف می‌کنند، هوک‌ها چه زمانی اجرا می‌شوند و خروجی‌ها و فایل‌های موقت در کجا قرار می‌گیرند. این سند بازتابِ پیاده‌سازی واقعی در `build.py` است؛ هیچ بخشی از آن آرمانی (aspirational) نیست.

## نمای کلی

ایمیج‌های Yaran Linux سیستم‌های زنده (live) مبتنی بر دبیان هستند. یک مانیفست، یک سوئیت دبیان upstream، یک مجموعه بسته و فهرستی از هوک‌های سفارشی‌سازی را انتخاب می‌کند. `build.py` ابزارهای `debootstrap`، APT و `chroot` را هدایت می‌کند تا یک فایل‌سیستم ریشه (root filesystem) بسازد، سپس آن را در SquashFS بسته‌بندی می‌کند و با GRUB یک ISO قابل بوت با BIOS+UEFI مونتاژ می‌کند.

خود بیلدکننده به توزیع خاصی وابسته نیست: هیچ برندینگی از Yaran Linux در آن وجود ندارد. همه برندینگ‌ها، بسته‌ها و پیکربندی‌ها در مانیفست‌ها، `hooks/` و `assets/` قرار دارند.

## اجزای مخزن

| مسیر | نقش |
|---|---|
| `build.py` | بیلدکننده: بارگذاری و اعتبارسنجی پیکربندی، بوت‌استرپ، نصب بسته‌ها، اجرای هوک‌ها، مونتاژ SquashFS و ISO |
| `Yaran-2.0-*.json`، `Yaran-Server-2.0-amd64.json` | مانیفست‌های ایمیج: یک فایل JSON برای هر نسخه (edition) منتشرشده |
| `Yaran-2.0-amd64.json` | مانیفست قدیمی تک‌دسکتاپ، که برای سازگاری نگه داشته شده و توسط CI ساخته نمی‌شود |
| `hooks/common/` | هوک‌های مشترک ایمیج‌های دسکتاپ و سرور (Calamares، Fastfetch، گواهی‌های CA، پاک‌سازی دارایی‌ها) |
| `hooks/desktop/` | هوک‌های اختصاصی دسکتاپ (دارایی‌های Plasma، ورود خودکار SDDM، فایروال، sysctl، مخازن فروشنده، برنامه‌های خارجی) |
| `hooks/server/` | هوک‌های اختصاصی سرور (نصب‌کننده CLI، journald، سیاست رمز عبور، فایروال، sysctl) |
| `scripts/ci-build.sh` | اسکریپت ساخت واحد دبیان که CI داخل یک کانتینر privileged اجرا می‌کند؛ نصب وابستگی‌ها، آزمون، اعتبارسنجی و ساخت |
| `assets/` | فایل‌های برندینگ که توسط هوک‌ها داخل ایمیج‌ها کپی می‌شوند: تم Plasma/SDDM، کاغذدیواره‌ها، پیکربندی Calamares، پیکربندی Fastfetch، فایل‌های نصب‌کننده سرور |
| `examples/` | مانیفست‌های نقطه شروع برای دیگر توزیع‌های خانواده دبیان |
| `tests/` | آزمون‌های واحد برای پیکربندی و مونتاژ، به‌همراه آزمون دود (smoke test) اختیاری بوت QEMU |
| `.github/workflows/` | CI: `build.yml` (اعتبارسنجی + ساخت نسخه‌ها)، `image.yml` (job ساخت قابل استفاده مجدد)، `release.yml` (ساخت‌های release) |

## خط لوله ساخت

متد `LiveBuilder.build()` این گام‌ها را به ترتیب اجرا می‌کند. هر گام یک بنر با نام خود چاپ می‌کند تا لاگ‌های ساخت دقیقاً نشان دهند خطا در کجا رخ داده است.

1. **آماده‌سازی دایرکتوری‌ها** (`prepare_dirs`) — رد کردن مسیرهای کاری/خروجی هم‌پوشان یا غیرخالی؛ ایجاد `chroot/`، `iso/live/`، `iso/boot/grub/` و `iso/.disk/` در زیر دایرکتوری کاری.
2. **بوت‌استرپ** (`run_debootstrap`) — اجرای `debootstrap` در `chroot/` با سوئیت، میرور، کامپوننت‌ها، variant و معماری پیکربندی‌شده. بسته `ca-certificates` در گام بوت‌استرپ نصب می‌شود تا دریافت‌های HTTPS از مخازن فروشنده در مراحل بعد کار کنند.
3. **mount فایل‌سیستم‌های شبه** — bind-mount کردن `/dev`، `/proc`، `/sys` و `/run` درون chroot؛ همه گام‌های chroot به آن‌ها نیاز دارند.
4. **هوک‌های پیش از chroot** (`pre_chroot_scripts`) — هوک‌های `pre_chroot_scripts` شما **روی میزبان** اجرا می‌شوند، با متغیر محیطی `ROOTFS` که به chroot اشاره می‌کند و دایرکتوری مانیفست به‌عنوان دایرکتوری کاری. اینجاست که Yaran Linux دارایی‌ها را آماده (stage) می‌کند و کلیدهای امضاشده مخازن فروشنده را پیش از نخستین به‌روزرسانی APT نصب می‌کند.
5. **پیکربندی APT** (`configure_apt`) — نوشتن `apt_sources` در `sources.list` و اجرای `apt-get update`.
6. **نصب بسته‌ها** (`install_packages`) — اعمال `exclude_packages` به‌صورت pinهای منفی APT، اجرای شبیه‌سازی وابستگی‌های APT، و سپس نصب `live_packages` + `kernel_package` + `packages` با غیرفعال‌بودن recommendها، مگر اینکه `install_recommends` برابر true باشد.
7. **پیکربندی کاربران** (`configure_users`) — ایجاد کاربر live و گروه‌ها، تنظیم یا قفل کردن رمزهای عبور بر اساس مانیفست، و قفل کردن root مگر اینکه رمز عبور root داده شده باشد.
8. **پیکربندی سیستم** (`configure_system`) — نام میزبان، locale، منطقه زمانی، بازنویسی‌های `os_release` و فهرست‌های فعال/غیرفعال/ماسک کردن `services`.
9. **هوک‌های پس از نصب** (`post_install_scripts`) — هوک‌های شما **درون chroot** به‌صورت اسکریپت‌های `bash -eu` اجرا می‌شوند. Yaran Linux پیکربندی دسکتاپ/سرور را در همینجا اعمال می‌کند.
10. **اعمال سرویس‌ها** — اجرای `systemctl` برای هر فهرست غیرخالی از `services.enable` / `disable` / `mask`.
11. **بازتولید initramfs** — اجرای `update-initramfs -u -k all` تا پیکربندی‌های نصب‌شده توسط هوک‌ها در تصویر بوت گنجانده شوند.
12. **پاک‌سازی chroot** — حذف کش‌ها و فایل‌های موقت هوک‌ها، پاک کردن لاگ‌ها و وضعیت machine-id، تا سیستم زنده تمیز بالا بیاید.
13. **برون‌بری کرنل و initrd** — کپی جدیدترین کرنل و initramfs متناظرش در `iso/live/` برای ورودی‌های GRUB.
14. **ساخت SquashFS** (`build_squashfs`) — بسته‌بندی chroot در `iso/live/filesystem.squashfs` با فشرده‌سازی پیکربندی‌شده (`xz` به‌صورت پیش‌فرض). دایرکتوری `/boot` داخل ایمیج حفظ می‌شود تا نصب‌کننده‌ای که فایل‌سیستم زنده را کپی می‌کند، کرنل و initramfs مربوط به سیستم نصب‌شده را در اختیار داشته باشد.
15. **نوشتن پیکربندی‌های بوت** (`write_boot_configs`) — تولید `grub.cfg` با ورودی‌های پیش‌فرض `live`، `live, nomodeset` و `live, debug` (به‌همراه هر ورودی سفارشی `grub_menu.entries`)، و ساخت تصاویر GRUB برای BIOS و UEFI، از جمله تصاویر بوت El Torito برای رسانه‌های قابل بوت با BIOS.
16. **ساخت ISO** (`build_iso`) — مونتاژ ایمیج با `xorriso`، نوشتن آن در یک فایل موقت `.partial` در دایرکتوری خروجی، محاسبه SHA-256 آن، و انتشار اتمیک ISO به‌همراه فایل `.iso.sha256`.

## هوک‌ها: پیش از chroot در برابر پس از نصب

این دو فهرست هوک در مراحل و محیط‌های متفاوتی اجرا می‌شوند:

| | `pre_chroot_scripts` | `post_install_scripts` |
|---|---|---|
| زمان اجرا | روی میزبان، پیش از پیکربندی APT | درون chroot، پس از نصب بسته‌ها و پیکربندی سیستم |
| محیط | ابزارزنجیره (toolchain) و شبکه میزبان؛ متغیر `$ROOTFS` روی chroot تنظیم شده | خود سیستم مقصد |
| کاربرد معمول | آماده‌سازی دارایی‌ها، نصب کلیدهای مخازن طرف سوم | نصب و پیکربندی برنامه‌ها، تم‌ها و فایل‌های سرویس |
| نمونه‌های Yaran Linux | `hooks/desktop/stage-assets.sh`، `hooks/desktop/vendor-repos.sh` | `hooks/desktop/plasma-assets.sh`، `hooks/common/install-calamares.sh` |

ورودی‌های هوک می‌توانند مسیر باشند (نسبت به دایرکتوری مانیفست resolve می‌شوند) یا اسکریپت‌های درون‌خطی (inline). هوک‌های پیش از chroot نیز دایرکتوری مانیفست را به‌عنوان دایرکتوری کاری خود دارند، بنابراین فراخوانی بیلدکننده از یک دایرکتوری دیگر، کپی‌های نسبی دارایی‌ها را خراب نمی‌کند. هوک‌ها با Bash و پرچم `-eu` اجرا می‌شوند؛ کدی قابل‌اعتماد هستند که با دسترسی root اجرا می‌شود و خطاها، بیلد را قطع می‌کنند. هوک‌های chroot در فایل‌های موقت کپی می‌شوند و حتی در صورت خطا نیز حذف می‌گردند.

## دارایی‌ها (Assets)

`assets/` همه چیزی را در خود نگه می‌دارد که هوک‌ها داخل ایمیج‌ها کپی می‌کنند:

- `assets/yaran-plasma-theme/` — ظاهر و حس (look-and-feel) Plasma، صفحه ورود SDDM، طرح رنگ و مقادیر پیش‌فرض، که به‌صورت یک درخت FHS (`usr/`، `etc/`) چیده شده‌اند و هوک‌ها آن‌ها را در chroot کپی می‌کنند؛ [راهنمای تم](theme.fa.md) را ببینید.
- `assets/wallpapers/` — بسته‌های کاغذدیواری، که به‌عنوان پس‌زمینه GRUB نیز از طریق `grub_menu.background` استفاده می‌شوند.
- `assets/calamares/` — پیکربندی و برندینگ نصب‌کننده Calamares (`settings.conf`، `modules/`، `branding/` و ابزار کمکی `yaran-grub-install`).
- `assets/fastfetch/` — پیکربندی و لوگوی Fastfetch که در نشست‌های تعاملی Bash نمایش داده می‌شود.
- `assets/server/` — نصب‌کننده CLI سرور: فایل `/usr/local/bin/install-yaran`، قانون sudoers مربوطه، و واحد `yaran-installer.service` که آن را روی کنسول زنده آغاز می‌کند.

ایمیج‌های دسکتاپ دارایی‌ها را در `/.temp_assets/` داخل chroot آماده می‌کنند (`stage-assets.sh`)، در هوک‌های بعدی از آن‌ها استفاده می‌کنند و دایرکتوری موقت را در `cleanup-assets.sh` حذف می‌کنند تا هیچ چیز موقتی در ایمیج باقی نماند.

## آزمون‌ها

- `tests/test_config.py` — اعتبارسنجی پیکربندی، resolve مسیر هوک‌ها، مدیریت خطای mount/unmount، pin کردن APT برای مستثنی‌ها، برون‌بری کرنل و تولید ورودی‌های بوت. نیازی به root ندارد.
- `tests/test_boot_image.py` — آزمون رگرسیون برای مونتاژ تصویر بوت BIOS (که از باگ CD loader ناقص جلوگیری می‌کند).
- `tests/test_iso_integration.py` — آزمون دود اختیاری (که مگر `RUN_BOOT_SMOKE=1` باشد skip می‌شود) که یک ISO فیکسچر GRUB می‌سازد و آن را در QEMU، با BIOS و (با OVMF) با UEFI بوت می‌کند.

## خروجی‌ها و فایل‌های موقت

| مسیر | محتوا | طول عمر |
|---|---|---|
| دایرکتوری کاری (`--workdir` یا یک دایرکتوری موقت) | `chroot/`، `iso/`، کتابداری mountها | پس از بیلد موفق حذف می‌شود، مگر با `--keep-workdir`؛ **پس از خطا نگه داشته می‌شود** تا بررسی شود |
| دایرکتوری خروجی (`--outdir`، پیش‌فرض `output/`) | ISO و فایل `.iso.sha256` | دائمی؛ نام‌های ISO موجود رد می‌شوند |
| `__pycache__/`، `*.log` | بایت‌کد Python، لاگ‌ها | توسط Git نادیده گرفته می‌شوند؛ حذفشان بی‌خطر است |

هر دو الگوی `build/` و `output/` در `.gitignore` پوشش داده شده‌اند. پیش از حذف دستی یک دایرکتوری کاری ناموفق، مطمئن شوید هیچ چیزی در زیر آن هنوز mount نشده است (`mount | grep <workdir>`)؛ بیلدکننده هنگام نگه‌داشتن یک دایرکتوری کاری، یک هشدار چاپ می‌کند.

## معماری CI

`build.yml` یک job با نام `validate` را اجرا می‌کند (آزمون‌های واحد، اعتبارسنجی `--validate` همه مانیفست‌ها، و اجرای `bash -n` روی همه اسکریپت‌های shell) و سپس برای هر نسخه به workflow قابل استفاده مجدد `image.yml` می‌تازد: نسخه‌های Minimal و Extended روی `ubuntu-latest`، نسخه ARM64 روی یک runner بومی `ubuntu-24.04-arm`، و نسخه Server روی `ubuntu-latest`. هر job از `image.yml` دستور `docker run --privileged debian:trixie bash scripts/ci-build.sh <manifest>` را اجرا می‌کند و لاگ را (همیشه) و به‌همراه آن ISO + checksum را (در صورت موفقیت) آپلود می‌کند. `release.yml` همین کار را برای هر نسخه هنگام انتشار یک GitHub release انجام می‌دهد و فایل‌ها را به release پیوست می‌کند. جزئیات را در [Releases](releases.fa.md) ببینید.
