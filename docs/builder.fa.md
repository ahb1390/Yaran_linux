# ساخت ایمیج‌های زنده خانواده دبیان

`build.py` یک مانیفست JSON مصرف می‌کند و یک ISO زنده (live) می‌سازد. برندینگ Yaran Linux، بسته‌ها و هوک‌ها در مانیفست‌ها و دایرکتوری `hooks/` قرار دارند، نه در خود بیلدکننده. برای اجرا به Python نسخه ۳.۹ یا جدیدتر نیاز است و هیچ ماژول سوم‌طرفه‌ای از Python لازم نیست.

## شروع با یک توزیع دیگر

فایل `examples/debian-minimal.json` یا `examples/ubuntu-minimal.json` را کپی کنید. سوئیت upstream، میرور بوت‌استرپ، کامپوننت‌ها و سورس‌های APT، بسته کرنل و بسته‌های اضافی خود را تنظیم کنید. نمونه Ubuntu از پیاده‌سازی `live-boot` دبیان که در مخزن universe اوبونتو موجود است استفاده می‌کند، نه از Casper. این نمونه‌ها نقطه شروع هستند، نه انتشارهای کاملاً آزموده‌شده توزیع.

```sh
python3 build.py examples/debian-minimal.json --validate
sudo python3 build.py examples/debian-minimal.json --workdir build-debian --outdir output-debian
```

اعتبارسنجی به root، ابزارهای ساخت یا دسترسی شبکه نیاز ندارد. این مرحله انواع، نام‌ها، مسیرها و تناقض‌های پیکربندی را بررسی می‌کند؛ اما وجود بسته‌ها در مخازن ریموت را بررسی نمی‌کند. بیلدهای واقعی پیش از نصب بسته‌ها، شبیه‌سازی وابستگی‌های APT را اجرا می‌کنند. خطاهای مخزن و بسته، فازِ (phase) شکست‌خورده را نیز شامل می‌شوند.

## پیش‌نیازهای میزبان

میزبان باید لینوکس باشد، با mount و chroot‌های کارا، و باید با دسترسی root اجرا شود. از یک میزبان/کانتینر amd64 یا arm64 یا armhf بومی (native) مطابق با مانیفست استفاده کنید؛ بیلدکننده زمانی که خروجی `dpkg --print-architecture` با فیلد `architecture` مانیفست متفاوت باشد، از شروع کار خودداری می‌کند. ایمیج‌های amd64 شامل پشتیبانی BIOS و UEFI هستند؛ ایمیج‌های ARM برای ماشین‌هایی طراحی شده‌اند که از GRUB مبتنی بر UEFI و کرنل انتخاب‌شده پشتیبانی می‌کنند، نه فریم‌ورهای بوت اختصاصی برد (board). بوت‌استرپ معماری متقابل (cross-architecture) و امضای Secure Boot پیاده‌سازی نشده‌اند. معماری‌های دیگر به نگاشت‌های اضافی کرنل و GRUB و پشتیبانی از مونتاژ بوت نیاز دارند.

بیلدکننده همچنین به ابزارهای زیر در PATH میزبان نیاز دارد: `dpkg`، `debootstrap`، `mksquashfs`، `xorriso`، `mmd`، `mcopy`، `mount`، `umount`، `chroot`، `grub-mkimage` و `mkfs.vfat`.

روی یک میزبان دبیان با معماری amd64، این موارد را نصب کنید:

```sh
sudo apt-get install debootstrap debian-archive-keyring ca-certificates \
  squashfs-tools grub2-common grub-pc-bin grub-efi-amd64-bin grub-efi-ia32-bin \
  xorriso mtools dosfstools python3 xz-utils
```

بستهٔ `xz-utils` استخراج `tar -xJf` برای آرشیوهای `.tar.xz` را روی میزبان ساخت ممکن می‌کند؛ هوک نصب Node.js علاوه بر آن به ماژول `lzma` کتابخانهٔ استاندارد پایتون هم رجوع می‌کند، بنابراین روی میزبان‌های بدون باینری `xz` هم کار می‌کند.

برای ARM به‌جای بسته‌های GRUB مربوط به amd64/BIOS، از بسته متناظر `grub-efi-arm64-bin` یا `grub-efi-arm-bin` استفاده کنید. مسیر `/usr/sbin` را در PATH کاربر root قرار دهید. برای یک مشتق (derivative) از دبیان به یک اسکریپت سوئیت debootstrap و کلید امضای آرشیو نیاز است که باید روی میزبان در دسترس باشند؛ برای اوبونتو از یک میزبان ساخت مناسب اوبونتو استفاده کنید یا keyring آرشیو آن را نصب کنید. فیلدهای `debootstrap_script` و `debootstrap_keyring` امکان انتخاب صریح این فایل‌ها را فراهم می‌کنند. هیچ میان‌بری برای دور زدن تأیید امضا وجود ندارد.

این بیلدکننده سیستم‌هایی را با چیدمان live-boot/initramfs-tools دبیان می‌سازد. یک مشتق با سیستم init دیگر می‌تواند `live_packages` را جایگزین کند و `services` را خالی بگذارد و سپس سیستم init خود را در هوک‌ها پیکربندی کند. صرفاً با تغییر نام توزیع، یک سوئیت بوت‌استرپ، کرنل یا پشته بوت زنده‌ی ناسازگار، سازگار نمی‌شود.

> **یادداشت امنیتی:** یک بیلد کامل `debootstrap`، هوک‌های شما و اسکریپت‌های maintainer بسته‌ها را با دسترسی root اجرا می‌کند و فایل‌سیستم‌های شبه (pseudo-filesystems) را در زیر دایرکتوری کاری mount می‌کند. بیلدها را فقط روی ماشین‌هایی که تحت کنترل شما هستند و با یک دایرکتوری کاری اختصاصی اجرا کنید، و هوک‌های طرف سوم را پیش از گنجاندن بازبینی کنید — هوک‌ها کد دلخواه با دسترسی root هستند.

## رابط خط فرمان

```text
python3 build.py CONFIG [--workdir DIR] [--outdir DIR] [--keep-workdir] [--validate]
```

| گزینه | مقدار پیش‌فرض | معنا |
|---|---|---|
| `CONFIG` | — | مسیر مانیفست JSON |
| `--workdir` | دایرکتوری موقت | دایرکتوری کاری برای chroot و ساختار درختی ISO |
| `--outdir` | `./output` | مکانی که ISO و فایل checksum آن در آن منتشر می‌شود |
| `--keep-workdir` | خاموش | نگه‌داشتن فایل‌های کاری پس از یک بیلد موفق |
| `--validate` | خاموش | اعتبارسنجی مانیفست؛ نیازی به root یا ابزارهای ساخت ندارد |

## ساخت یک ISO

همیشه ابتدا اعتبارسنجی کنید و سپس در دایرکتوری‌های کاری و خروجی جداگانه بسازید:

```sh
python3 build.py Yaran-2.0-amd64-minimal.json --validate
sudo python3 build.py Yaran-2.0-amd64-minimal.json \
  --workdir build-minimal --outdir output-minimal
```

یک بیلد موفق، ISO و یک فایل متناظر `.iso.sha256` را در دایرکتوری خروجی می‌نویسد. ISO ابتدا در یک فایل موقت `.partial` مونتاژ می‌شود و فقط پس از موفقیت `xorriso` به‌صورت اتمیک (atomically) منتشر می‌شود؛ بنابراین یک مونتاژ ناموفق هرگز ISO ناقصی را با نام نهایی باقی نمی‌گذارد. اگر ISOیی با همین نام از قبل وجود داشته باشد، رد می‌شود — یک دایرکتوری خروجی دیگر انتخاب کنید یا ابتدا فایل قدیمی را حذف کنید.

### ساخت در Docker (همان‌طور که CI انجام می‌دهد)

سیستم یکپارچه‌سازی مداوم (CI) هر ایمیج را داخل یک کانتینر دبیان با امتیاز کامل (`--privileged`) می‌سازد. می‌توانید این کار را روی هر میزبان لینوکسی با Docker به‌صورت محلی بازتولید کنید؛ کانتینر به پرچم `--privileged` نیاز دارد چون فرآیند ساخت عملیات mount و chroot انجام می‌دهد:

```sh
docker run --rm --privileged \
  -v "$PWD:/work" -w /work \
  debian:trixie bash scripts/ci-build.sh Yaran-2.0-amd64-minimal.json
```

این اسکریپت وابستگی‌های ساخت را برای معماری کانتینر نصب می‌کند، آزمون‌های واحد و اعتبارسنجی مانیفست را اجرا می‌کند و سپس بیلد کامل را انجام می‌دهد. برای کانتینرهای amd64، آزمون‌های دود (smoke test) بوت QEMU را نیز فعال می‌کند (`RUN_BOOT_SMOKE=1 REQUIRE_UEFI_SMOKE=1`)، که به QEMU و OVMF داخل کانتینر نیز نیاز دارند (که توسط همین اسکریپت نصب می‌شوند). خروجی‌ها در `output/` قرار می‌گیرند؛ تصویر کانتینر و هرگونه دسترسی شبکه از پیکربندی Docker شما پیروی می‌کند.

## فضاهای کاری، خروجی و خطاها

از یک دایرکتوری کاری اختصاصی و خالی استفاده کنید که از دایرکتوری خروجی جداست. یک دایرکتوری کاری غیرخالی یا مسیرهای هم‌پوشان رد می‌شوند. بیلدهای ناموفق فضای کاری را برای بررسی نگه می‌دارند؛ قابلیت ادامه خودکار (resume) وجود ندارد. پیش از حذف دستی یک فضای کاری ناموفق، همه mountهای باقی‌مانده را unmount کنید و برای تلاش بعدی از یک دایرکتوری کاری تازه استفاده کنید. خطاهای unmount، ساخت ایمیج و پاک‌سازی را متوقف می‌کنند؛ یک mount که busy گزارش شود، با فاصله‌گذاری (backoff) دوباره تلاش می‌شود و در نهایت پیش از آنکه بیلدکننده تسلیم شود، به‌صورت تنبل (lazily) جدا می‌شود.

بیلدهای موفق فایل‌های کاری را حذف می‌کند، مگر اینکه `--keep-workdir` تنظیم شده باشد؛ از جمله وقتی که خود بیلدکننده یک دایرکتوری کاری موقت انتخاب کرده باشد. خروجی نهایی یک ISO و یک checksum با پسوند `.iso.sha256` است. محتوای مخازن و زمان‌بندی (timestamps) آن‌ها pin نمی‌شوند، بنابراین تضمینی برای بازتولید بایت‌به‌بایت بیلدها وجود ندارد.

## بیلدهای CI و مصنوعات (Artifacts)

CI از runnerهایی با معماری بومی و اسکریپت ساخت مشترک دبیان `scripts/ci-build.sh` استفاده می‌کند. ابتدا آزمون‌های واحد و اعتبارسنجی مانیفست اجرا می‌شوند؛ سپس بیلد چهار نسخه (edition) فقط پس از موفقیت job اعتبارسنجی آغاز می‌شود. هر job لاگ ساخت خود را حتی در صورت شکست بیلد به‌عنوان یک artifact آپلود می‌کند؛ jobهای موفق `output/*.iso` و `output/*.sha256` را آپلود می‌کنند. انتشار یک GitHub release این فایل‌ها را علاوه بر این، به release نیز پیوست می‌کند. برای مراحل دانلود و تأیید صحت، [Releases](releases.fa.md) را ببینید.

## اعتبارسنجی

```sh
python3 -m unittest discover -s tests -v
for config in Yaran*.json examples/*.json; do
  python3 build.py "$config" --validate
done
find hooks scripts -name '*.sh' -exec bash -n {} \;
```

پیش از توزیع یک ایمیج، یک بیلد کامل و بوت ماشین مجازی با BIOS/UEFI باید بررسی شود. با تنظیم `RUN_BOOT_SMOKE=1`، یک فیکسچر GRUB نیز در QEMU مونتاژ و بوت می‌شود. این کار به ماژول‌های GRUB برای amd64 و ابزارهای QEMU و ISO نیاز دارد؛ OVMF بررسی UEFI را فعال می‌کند (`REQUIRE_UEFI_SMOKE=1` باعث می‌شود نبودِ OVMF به‌جای skip، خطا محسوب شود). CI هر دو بررسی BIOS و UEFI را برای amd64 الزامی می‌کند. این فیکسچر هیچ سیستم‌عاملی شامل نمی‌شود.

آزمون‌های واحد رفتار پیکربندی و مونتاژ را اعتبارسنجی می‌کنند، نه وجود همه بسته‌ها و نه کارکرد دسکتاپ را. نمونه‌های minimal رمزهای عبور را قفل کرده‌اند؛ برای آزمایش در ماشین مجازی یک رمز عبور موقت آزمایشی یا یک تنظیم ورود خودکار (autologin) مناسب انتخاب کنید.

## خطاهای رایج

| علامت | علت محتمل | محل بررسی |
|---|---|---|
| `Working directory must be empty` | استفاده مجدد از دایرکتوری کاریِ یک بیلد ناموفق | با یک دایرکتوری تازه شروع کنید؛ ابتدا mountهای باقی‌مانده را unmount کنید |
| `Use a native <arch> host/container` | تلاش برای بیلد معماری متقابل | از یک میزبان یا کانتینر مطابق استفاده کنید |
| `Unknown configuration keys` | اشتباه تایپی در یک کلید مانیفست | [مرجع مانیفست](manifest.fa.md) را ببینید |
| `Package ... has no installation candidate` | نبودِ بسته در مخازن پیکربندی‌شده | فازِ شکست‌خورده چاپ می‌شود؛ `apt_sources` و سوئیت را بررسی کنید |
| شکست debootstrap یا دریافت کلید | مشکل شبکه، میرور یا TLS/گواهی | لاگ ساخت، مرحله شکست‌خورده را نام می‌برد؛ `ca-certificates` در بوت‌استرپ نصب می‌شود |
| خطاهای GRUB/xorriso در پایان کار | نبودِ بسته‌ها یا ماژول‌های GRUB برای معماری مقصد | بسته‌های GRUB فهرست‌شده در [پیش‌نیازهای میزبان](#پیش‌نیازهای-میزبان) را نصب کنید |

برای علائمی که ادامه می‌یابند، [Troubleshooting](troubleshooting.fa.md) را ببینید.
